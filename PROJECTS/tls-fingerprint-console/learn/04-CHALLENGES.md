# Challenges

Four defects were found by running the console over a real capture, and three of them share a shape worth naming: every rule was correct in isolation and dead in the integrated system.

**first_seen could never fire.** The ingest endpoint stored each event before it evaluated the rules, and `first_seen` asks the store whether it has already seen a fingerprint value. Because the value had just been written, the answer was always yes, and the rule that was supposed to announce a new value was silent on every value that ever arrived. The fix was to evaluate the rules first and store afterwards, which is a one-line reordering with a consequence far larger than its size.

**os_mismatch could never fire.** The rule compares the operating system a User-Agent declares against the operating system mapped from the event's JA3, and it needs that mapping handed to it. The application never built or supplied the map, so the rule had nothing to compare against and returned nothing on every event. The fix was to derive the map from the corpus and pass it into the evaluation context.

**known_bad could never fire.** The rule was written to fire when an event already carried an intel verdict, on the assumption that something upstream would attach one. Nothing did, so the rule waited forever for a field that was never set. The fix was to have the rule consult the corpus itself, so a fingerprint that matches the malware list raises the alert regardless of what the caller remembered to attach.

**A TLS record could be parsed as an HTTP request.** The HTTP parser accepted any byte stream whose first line was non-empty. A TLS record begins `0x16 0x03`, which is not a request line and not empty, so the parser accepted it and produced a JA4H computed from a record header rather than from a request. The pipeline compounded it by handing whole TLS streams to the same parser. The fix was to validate the request line strictly — exactly a method, a target and a version, with the method on a known list and the version matching `HTTP/x.y` — so a stream that is not an HTTP request is rejected rather than misread.

What makes these worth recording is that the unit tests passed throughout. Each rule had been tested against a hand-built event and a stub context, and against those inputs every rule behaved. The defects lived in the seams — in the order two calls were made, in a context key that was never populated, in a dependency the caller was expected to supply and did not. The response was an integration suite that drives the real store, corpus and rules through the real endpoint and asserts that every rule can fire through the app, because a rule that only fires under a stub is not a working rule.

## The live path

The four defects above were all found on the file path. The live path was built later and produced four more, and they share a different shape: each was a decision that looked correct in isolation and was only falsified by a stream of real packets.

**The sensor judged flow age against the wall clock.** A flow is retired once it has been idle for a while, and the sensor measured that idleness with `time.time()`. For a live capture that is right, because the packet timestamps track real time. It is wrong for a replayed capture, whose packets carry the timestamps of when they were recorded: against the wall clock every flow looked years stale the moment it was created, so it was expired before it could be emitted and the run produced nothing at all. The fix was to run the sensor on the packet clock — the largest timestamp it has seen — so a replay is judged by its own time and a live run is judged by a clock that agrees with the wall anyway.

**The ClientHello branch was skipped once the client was already known.** A TCP SYN carries the options JA4T is built from, so the sensor reads the client's identity out of the SYN and marks that side as the client. That inference is correct, and it was being made before the payload was examined — so the code that looks for a ClientHello only ran when the client was still unknown. On a live flow the SYN always arrives first, so the client was always already set, the ClientHello branch never ran, and JA3 and JA4 — the two fingerprints the console exists to produce — were absent from every live event. The fix was to look for the ClientHello independently of whether a client had been guessed, and to let the handshake confirm the side the SYN had proposed.

**A SYN set the client but not the server.** The same early inference marked the SYN's sender as the client but left the server unset, and the emit path reads the server endpoint from that field. For a TLS flow the ClientHello filled it in; for a plaintext HTTP flow, which has no handshake to name the other side, the destination came out empty and the event pointed at nowhere. The fix was to derive the server from the flow key whenever the client is known, in the HTTP branch as well as the TLS one.

**The event was released before the certificate arrived.** The sensor first emitted a flow as soon as the server answered. A server answers in several packets — the ServerHello first, the Certificate next — so the event went out carrying JA3S and JA4S and no JA4X, and the certificate fingerprint, one of the more distinctive values the console computes, was silently missing from live events while it was present in the same flow read from a file. The fix was to emit on quiescence rather than on the first server packet: wait until the server has answered and the flow has gone idle, with a hard cap so a busy connection is still released.

All four were found by running the console against real traffic on a real interface, not by the unit tests. The tests fed the sensor hand-built packets in a convenient order, and against that order every one of these defects was invisible; a real interface delivers a SYN before a ClientHello, answers in more packets than one, and can carry timestamps from a capture that is old. The lesson is the one the file path taught as well: the defects live in the seams, and the seams only show under real input.

## The boundaries

The limits are part of the design, not apologies for it. The console never decrypts, so it fingerprints only the handshake and a JA4H can only ever describe a plaintext HTTP flow. It reads a pcap, watches a live interface, or accepts posted events, and whichever path it takes it never transmits anything: it reads only what passes or what was recorded, so it sees the traffic in front of it and nothing more. Live capture is the one path with a dependency outside the standard library — it needs Npcap installed and, normally, an elevated shell — while the file and ingest paths need neither. The capture reader covers Ethernet and raw-IP link types across pcap and pcapng, with IPv4, IPv6 and VLAN decoding, and does not attempt link types outside that set.

The reference set ages. It is a snapshot of two public feeds plus a few curated entries, it is not refreshed automatically, and a malicious fingerprint absent from it will not match — so the console's silence is never evidence that a client is clean. `os_mismatch` cannot separate macOS from Linux, because a JA3 names a TLS stack and the two often share one, so the rule treats the Unix family as consistent and fires only on a real contradiction between families. `ua_mismatch` depends on a built-in table of client families and produces no verdict for a fingerprint it does not recognise, preferring silence to a guess. And the certificate parsing behind JA4X is hand-written to the published examples and the common structure of a certificate, not to every extension an X.509 certificate can carry.

None of these is a defect to be fixed later; they are the honest edges of a passive, structure-based tool. The console states them where it states what it can do, so a reader can weigh a match against what the tool could not have seen.
