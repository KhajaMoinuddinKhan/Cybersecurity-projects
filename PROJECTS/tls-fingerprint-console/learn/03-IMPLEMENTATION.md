# Implementation

The fingerprints live in `src/ja3.py` and `src/ja4.py`, and both take the same dict that `src/tls.py` produces. The parser returns cipher suites, extensions, curves, point formats, signature algorithms and supported versions in wire order and still containing GREASE, and it also reports the GREASE values it saw in a separate `grease` list. The fingerprint modules strip GREASE themselves rather than depending on the parser to have done it, which keeps the parser a faithful record of what was on the wire and the fingerprints the place where the interpretation happens.

**GREASE is stripped, then the lists are sorted — or not.** JA3 preserves order in every field, which is the original specification and the reason JA3 distinguishes two stacks that offer the same suites differently. JA4 sorts the cipher list and the extension list into hex order before hashing, because its purpose is to name the set of capabilities rather than the exact presentation. JA4S is the exception on purpose: the server's extensions are hashed in the order they arrived, matching the published examples, because a server's response is not a menu to be reordered.

**JA4's extension hash drops two extensions.** The SNI and ALPN extensions are excluded from the sorted list before it is hashed, because both are already represented in the readable part of the fingerprint — the `d`/`i` flag and the ALPN code. Including them would hash the same fact twice and let a client change its fingerprint by toggling an extension that the readable part already reports.

**The signature algorithms are appended, not sorted.** After the sorted extension list, JA4 appends the signature algorithms in their original order, joined by an underscore. This is what the specification does, and it is why a change in the offered signature algorithms moves the extension hash even though the algorithm list is not part of the extension list itself.

**JA4X hashes OID bytes, not names.** The certificate fingerprint is built by walking the DER structure and collecting the issuer's RDN attribute-type OIDs, the subject's and the certificate extension OIDs, then hashing the DER-encoded bytes of each OID joined together. Hashing the encoded bytes rather than the dotted-decimal strings is what makes the implementation agree with the published worked example, and it means two certificates with the same structure share a value regardless of the names inside them. The DER walk is hand-written with a tag-length-value reader, so no X.509 library is needed; it handles the version, serial, algorithm, issuer, validity, subject, key and extension fields in the order a certificate must carry them, and an absent list hashes to a run of zeros rather than being omitted.

**Counts are padded and capped.** The cipher and extension counts in JA4 are written as two digits and never exceed `99`, so a client offering an implausibly long list cannot make the readable part ambiguous. Missing MSS and window scale in JA4T render as `0` rather than blank, so every JA4T has the same number of fields.

**The TCP option kinds are recorded with the no-op but without the padding.** The option parser keeps option kind 1 (the no-op) because it is significant to a fingerprint, but stops at kind 0 (end of options) rather than recording the padding that follows, so two SYNs with the same meaningful options but different padding produce the same JA4T.

**Rules run before the event is stored, and the ordering is load-bearing.** `first_seen` asks the store whether it has seen a fingerprint value before. If the event were written first, that question would always be answered yes and the rule could never fire. The pipeline and the ingest endpoint both evaluate the rules first and store afterwards, and the store maintains its fingerprint index on insert so the next event's question is answered against everything already recorded.

**The OS map is built from the corpus, not from a constant.** `os_by_ja3()` walks the corpus and maps each JA3 to the operating-system family its source names. Only the salesforce list names a family, and it is the OSX/*nix client list, so every entry maps to the Unix family and no entry maps to Windows. That asymmetry is a fact about the corpus rather than a gap in the code, and it is why the rule can only ever fire on a genuine contradiction between families.

**The app is wired for substitution.** `create_app(store, corpus, rules_module=None)` takes its dependencies as arguments, resolves the rules module lazily and tolerates its absence. The same shape is why the test suite can drive the real endpoint against in-memory fakes, and why the app can be imported while a sibling module is still being written.

**The console is one file with no dependencies.** The page carries its own CSS and JavaScript inline and references no external asset, so it renders from the app with no network and nothing to install. It polls on a fixed interval and updates individual panels in place rather than rebuilding the page, and it reads the current filter and search values at render time, which is why what you typed survives the next poll.
