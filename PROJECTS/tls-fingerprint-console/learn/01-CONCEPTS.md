# Concepts

A fingerprint is a hash of the fields a client offers when it opens a TLS connection, not a hash of anything it sends afterwards. The ClientHello is a client introducing itself: here are the versions I speak, here are the cipher suites I know, here are the extensions I understand, here are the curves and signature algorithms I can use. The ServerHello is the server picking from that menu. Both are sent before any key is agreed, which is the only reason a tool that holds a capture and no keys can read them. Once the handshake completes, everything is ciphertext and stays that way here.

The same client produces the same fingerprint because a TLS stack is built, not improvised. The list of suites a browser offers is compiled into it and changes only when the browser does; the order the list is written in is a property of the library that wrote it. Two copies of the same browser on two machines offer the same lists in the same order, so they hash to the same value, and a fingerprint becomes a name for the software rather than for the machine.

GREASE is the reason a naive fingerprint would never be stable. Modern clients deliberately insert reserved values — `0x0a0a`, `0x1a1a`, `0x2a2a` and their siblings up to `0xfafa` — into their cipher, extension and curve lists. The values are reserved precisely so that a server must ignore them, and a client picks them fresh on every connection so that any middlebox that fails to ignore them will break in a detectable way. A fingerprint that kept them would change on every handshake and describe nothing. So the first thing every fingerprint function does is drop GREASE, and a client that pads its offer with GREASE produces the same value as one that does not.

JA3 and JA4 differ in how much they trust the wire order. JA3 keeps the cipher, extension, curve and point-format lists exactly as they arrived, which makes it precise and also brittle: a client that offers the same suites in a different order gets a different JA3. JA4 sorts the cipher list and the extension list into hex order before hashing, so a stack that shuffles its menu still lands on one value, and it puts the version, the presence of a server name, the counts and the ALPN in front of the hashes as readable characters. The sorted hash answers "which suites does this client know"; the readable part answers "and how did it present them".

The counts and flags in JA4's readable part are choices, not decoration. The version is taken from the highest version the client listed as supported, falling back to the version field of the record; the server-name flag is `d` when the SNI extension is present and `i` when it is not; the counts are zero-padded and stop at 99; and the ALPN code is the first and last character of the first protocol the client offered. Each of these turns a fact about the handshake into a couple of characters a reader can see without un-hashing anything.

A corpus is a lookup table of fingerprints with a category and a provenance. It does not decide anything by itself; it answers whether a given value has been named, and by whom, under what licence. The rules are what turn that answer into a decision, and every rule in this project is written to return nothing rather than a guess when it cannot establish its premise. An unknown fingerprint is not treated as benign, and it is not treated as suspicious either — it is treated as unknown, which is the only honest reading of a value no one has classified.

QUIC is the transport HTTP/3 runs on, and it is TLS 1.3 folded into a UDP protocol rather than TLS carried over TCP. That difference is why a tool that only watched TCP could not see it: the handshakes were there, and the filter excluded every one of them. What makes QUIC readable is a fact worth holding on to, because it sounds like a contradiction. A QUIC Initial packet is encrypted, and its keys are not secret. They are derived from a salt that the specification publishes and the destination connection ID that the client sends in the clear, so anyone who can see the packet can derive the same keys and read the ClientHello inside it. This is deliberate: the connection ID has to be readable for the packet to be routed, and the handshake that follows is what establishes the real keys. So a passive observer can fingerprint HTTP/3 for the same reason it can fingerprint TLS over TCP — the negotiation is readable — even though the mechanism that hides it looks, at first, like it should prevent exactly that.

Encrypted Client Hello is the opposite case, and it is the one where a tool has to be careful about what it claims. With ECH the client offers to hide its real handshake: the outer ClientHello a passive reader sees carries a public name in place of the real server name, and the real extension list is sealed inside an encrypted inner hello that only the server can open. The outer hello still parses, so a fingerprint can still be computed from it — but that fingerprint describes the deliberately generic shell, not the software behind it, and the server name beside it is a decoy. What ECH hides is not the fact that a connection happened, but which site it is for and which client is really making it, and the honest response is to report the value and the caveat together rather than to hand over a fingerprint that looks authoritative and is not. The extension itself is only an offer: Chrome offers ECH to every host it contacts, including hosts that publish no ECHConfig, and it shapes the offer like a real one, so the caveat has to say that the value *may* be a decoy rather than that it certainly is.

Live capture makes that claim observable rather than theoretical. Watching a real interface for a short while shows a client library reaching one destination after another, and every one of those connections carries the same JA3 and JA4, because the fingerprint describes the stack that made the connection and not the name it connected to. One client, many destinations, one fingerprint is the whole idea in a single run, and the console's live path exists to put that in front of you as it happens; the concept it demonstrates is the one this note has been describing throughout.
