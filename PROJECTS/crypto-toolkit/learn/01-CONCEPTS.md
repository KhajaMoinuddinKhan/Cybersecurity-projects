# Concepts

**A block cipher is not a mode.** AES takes sixteen bytes and a key and returns sixteen bytes. That is the whole primitive. Everything that makes it useful for a message of any length -- counter mode, GCM, CBC -- is a construction built on top, and each construction has its own failure modes. Keeping the two separate in the code is what lets the block cipher be tested against the standard's own vectors, with nothing else in the way.

**GF(2**8) and GF(2**128) are the same idea at two sizes.** Both are fields of polynomials over the two-element field, where addition is XOR and multiplication is a shift and a conditional XOR with a fixed reduction polynomial. AES uses the small one: the S-box is the multiplicative inverse of a byte in GF(2**8) followed by an affine transform, and the column mixing is a multiplication by a fixed polynomial. GHASH uses the large one, on 128-bit blocks. The difference that catches people is the bit ordering. In GF(2**8) the convention is the ordinary one; in GHASH the specification numbers the bits so the leftmost bit of a block is the coefficient of x**0, which means the shift runs to the right and the reduction polynomial is applied when the *low* bit falls off.

**A tag is a polynomial evaluation, not a checksum.** GCM's tag is the ciphertext and the associated data, seen as one long polynomial, evaluated at a point derived from the key. Change any coefficient and the value changes unpredictably; without the key, you cannot compute the new value. That is why a tag can be short and still be worth trusting, and why getting the polynomial arithmetic subtly wrong produces tags that verify against nothing.

**Why the length block carries bits and not bytes.** GHASH's final block is the two input lengths, and the specification states them in bits. A message of sixty bytes and a message of sixty bits would otherwise hash identically. The unit is easy to get wrong, and when it is wrong every tag is wrong, so the code names it in the docstring and a test asserts that one byte of associated data is not the same input as one byte of ciphertext.

**Why HMAC pads the key.** The construction XORs the key with two fixed constants and hashes the result. If the key is shorter than the hash's block size, it is right-padded with zeros first, and if it is longer it is hashed down to the digest size and then padded. Skip the second rule and short keys work while long ones fail, which is exactly the kind of bug the published vectors include a long-key case to catch.

**Why an oracle is not a shortcut.** The tests compare this implementation against the standard library for SHA-256 and HMAC, and against an installed cryptography package for AES and GCM. That is not the code borrowing an implementation; it is the tests borrowing a second opinion. A primitive tested only against its own expected output is being asked to mark its own homework.
